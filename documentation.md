## 1. What MedVault Is

MedVault is a security-focused medical records backend built for healthcare facilities in Kigali,
Rwanda. It sits on top of existing hospital infrastructure as a protection layer â€” it does not
replace your EMR system, it secures it.

**What it gives you out of the box:**

- Multi-factor authentication (password + TOTP via Google Authenticator)
- Role-based access control across 7 staff roles
- Patient-controlled, time-limited consent grants for doctor access
- AES-256-GCM field-level encryption on every medical record
- A tamper-evident, SHA-256 hash-chained audit log
- Replay attack prevention on all state-changing endpoints
- A browser-based portal for all roles â€” no Postman required

**Tech stack:** Python 3.11+, FastAPI, PostgreSQL 15+, SQLAlchemy 2 (async), Alembic, PyJWT,
bcrypt, custom RFC 6238 TOTP, AES-256-GCM, TLS 1.2+.

## 4. Database Setup

MedVault uses PostgreSQL. Create the database and a dedicated user before running migrations.

**Connect to PostgreSQL as the superuser:**

```bash
# Linux / macOS
psql -U postgres

# Windows (use the full path if psql is not on PATH)
& "C:\Program Files\PostgreSQL\18\bin\psql.exe" -U postgres
```

**Run these SQL commands:**

```sql
-- Create the application database
CREATE DATABASE medrecords;

-- (Optional but recommended for production)
-- Create a dedicated application user with limited privileges
CREATE USER medvault_user WITH PASSWORD 'choose_a_strong_password';
GRANT ALL PRIVILEGES ON DATABASE medrecords TO medvault_user;

-- Exit
\q
```

> For development you can use the `postgres` superuser directly, as shown in the `.env` example
> below. For production, use the dedicated user and restrict its privileges after migrations run.

**Key generation commands (run once, save the output):**

```bash
# JWT secret
openssl rand -hex 32

# Record encryption key
python -c "import os,binascii; print(binascii.hexlify(os.urandom(32)).decode())"

# TOTP encryption key (run again to get a different key)
python -c "import os,binascii; print(binascii.hexlify(os.urandom(32)).decode())"
```

> The application refuses to start if any of these keys is missing or if an encryption key is
> not exactly 32 bytes (64 hex characters). This is intentional â€” a misconfigured key would
> silently corrupt all encrypted data.



## 6. TLS Certificate Generation

All traffic must go over HTTPS. For development, generate a self-signed certificate:

```bash
openssl req -x509 -newkey rsa:4096 -keyout key.pem -out cert.pem \
  -days 365 -nodes \
  -subj "/C=RW/ST=Kigali/O=MedVault/CN=localhost" \
  -addext "subjectAltName=DNS:localhost,IP:127.0.0.1"
```

This creates two files in the project root:

| File | Contents | Keep secret? |
|------|----------|-------------|
| `cert.pem` | Public certificate â€” sent to every browser | No |
| `key.pem` | Private key â€” stays on the server | **Yes** |

> **Never commit `key.pem` to version control.** It is already in `.gitignore`.
>
> For production, replace these files with a CA-signed certificate (e.g., from Let's Encrypt).
> Update `TLS_CERT_FILE` and `TLS_KEY_FILE` in `.env` to point to the new paths. No code change
> is needed.

## 8. Running Database Migrations

Alembic manages the schema. Run all migrations from the project root:

| 003 | Admin and SuperAdmin roles; consent_grants table |
| 004 | must_change_password flag on users |
| 005 | email_otp table |
| 006 | recovery_email column on users |

| 009 | Record draft/publish status; patient_profiles; emergency_contact_links |

To check the current migration state:


```bash

```

## 12. API Reference

All endpoints require HTTPS. State-changing endpoints additionally require two headers:

```
X-Nonce: <uuid-v4>
X-Timestamp: <ISO-8601 UTC, e.g. 2026-04-22T20:00:00Z>
```

The timestamp must be within Â±5 minutes of server time. The nonce must be unique per request.

## 14. Running the Attack Demonstrations

The `attacks/` folder contains 11 scripts that demonstrate security attacks and confirm the
defences are active. Run them all at once:

```bash
python attacks/run_all.py
```

Or run individually:

```bash
python attacks/01_replay_attack.py
python attacks/02_stale_timestamp.py
python attacks/03_privilege_escalation.py
python attacks/04_jwt_forgery.py
python attacks/05_user_enumeration.py
python attacks/06_brute_force.py
python attacks/08_unauthorized_record_access.py
python attacks/09_cross_patient_access.py
python attacks/10_draft_record_leakage.py
python attacks/11_aes_gcm_tampering.py
```

**Attacks 07 and 11 require direct database access** because they simulate an insider threat
at the database level â€” something that cannot be done through the API alone.

### Attack 07 â€” Audit Log Tampering

```bash
# Connect to the database
& "C:\Program Files\PostgreSQL\18\bin\psql.exe" -U postgres -d medrecords

# See the first few audit entries
SELECT id, event_type, chain_hash FROM audit_log ORDER BY id LIMIT 3;

# Tamper with the first entry
UPDATE audit_log
SET event_type = 'TAMPERED_BY_ATTACKER'
WHERE id = (SELECT MIN(id) FROM audit_log);

# Exit psql, then call the verify endpoint
# GET /audit/verify â€” it will report chain_intact: false
```

The system reports the exact entry where the chain breaks, the actor UUID, and the timestamp.
The actor UUID can be resolved to a real user:

```sql
SELECT id, email, full_name, role FROM users WHERE id = '<actor_uuid>';
```

### Attack 11 â€” AES-GCM Ciphertext Tampering

```bash
# Find a record ID first (from the portal or API)
# Then flip one byte in the ciphertext
UPDATE medical_records
SET encrypted_data = set_byte(encrypted_data, 0, get_byte(encrypted_data, 0) # 255)
WHERE id = '<record_uuid>';
```

The next read of that record returns HTTP 500 â€” the AES-GCM authentication tag detects the
modification and decryption is aborted before any plaintext is returned.

## 16. Production Checklist

Before deploying to a real hospital environment, complete every item on this list.

- [ ] Replace the self-signed TLS certificate with a CA-signed one (Let's Encrypt or institutional CA)
- [ ] Set `DEV_MODE=False` in `.env`
- [ ] Change the SuperAdmin default password
- [ ] Move secrets from `.env` to a secret manager (AWS Secrets Manager, HashiCorp Vault, or equivalent)
- [ ] Restrict the PostgreSQL application user to `INSERT, SELECT` on `audit_log` and appropriate privileges on other tables
- [ ] Enable PostgreSQL SSL connections (`sslmode=require` in `DATABASE_URL`)
- [ ] Set up automated database backups
- [ ] Configure a reverse proxy (nginx or Caddy) in front of Uvicorn for production traffic
- [ ] Set `allow_origins` in `app/main.py` to your actual domain instead of the wildcard ngrok URL
- [ ] Enable server-side rate limiting (e.g., via nginx or a FastAPI middleware)
- [ ] Set up log aggregation for the Uvicorn access log and application errors
- [ ] Test the password reset email flow with your production SMTP credentials



## 17. Troubleshooting

**Server exits immediately on startup**

Check that all required environment variables are set and that both encryption keys are exactly
64 hex characters. The Key Manager prints a descriptive error identifying the missing variable.

**`[Errno 10048]` â€” port already in use**

Another process is already on port 8000. Find and stop it:

```powershell
netstat -ano | findstr ":8000"
Stop-Process -Id <PID> -Force
```

**`psql` not recognized**

Add the PostgreSQL bin directory to your PATH:

```powershell
$env:PATH += ";C:\Program Files\PostgreSQL\18\bin"
```

**Browser shows "Not Secure" warning**

This is expected with a self-signed certificate. Click Advanced â†’ Proceed to localhost. For
production, use a CA-signed certificate to eliminate this warning.

**`LOGIN_FAILED` events not appearing in the audit log**

This means the server is running old code. Restart it â€” the fix that writes failed logins in
a separate committed session requires the new `auth_service.py` to be loaded.

**Audit chain shows `chain_intact: false`**

Someone ran the Attack 07 demonstration and modified the audit log directly in the database.
This is expected after running `attacks/07_audit_tampering.py`. To restore a clean chain for
further testing, either restore the database from a backup or truncate the audit log and restart
(development only â€” never truncate in production).

**Email not sending**

Check your SMTP credentials in `.env`. In development, set `DEV_MODE=True` â€” password reset
tokens will be returned in the API response instead of emailed, so you can test without SMTP.

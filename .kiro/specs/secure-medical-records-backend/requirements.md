# Requirements Document

## Introduction

This document defines the requirements for the backend of a Secure Patient Medical Records System
designed for Rwandan healthcare institutions. The system exposes a RESTful API built with Python
and FastAPI, backed by PostgreSQL via SQLAlchemy ORM. It enforces multi-factor authentication,
role-based access control, patient-driven consent, AES-256 field-level encryption of medical
records, and an append-only tamper-evident audit log. The system is intended to be demoed locally
via Postman with self-signed TLS and must contain no hardcoded secrets.

---

## Glossary

- **System**: The Secure Patient Medical Records backend API.
- **Auth_Module**: The component responsible for user registration, login, JWT issuance, and MFA verification.
- **User_Module**: The component responsible for managing user accounts and role assignments.
- **RBAC_Middleware**: The middleware component that enforces role-based access control on every protected endpoint.
- **Consent_Module**: The component that manages doctor-initiated access requests and patient approval/revocation.
- **Records_Module**: The component that handles CRUD operations on medical records with AES-256 field-level encryption.
- **Audit_Module**: The component that writes append-only, hash-chained audit log entries.
- **Replay_Guard**: The component that validates nonce and timestamp on sensitive endpoints to prevent replay attacks.
- **Key_Manager**: The component responsible for loading and providing AES-256 encryption keys from environment configuration.
- **Patient**: A registered user with the Patient role who owns medical records.
- **Doctor**: A registered user with the Doctor role who may request and receive consent-gated access to Patient records.
- **Nurse**: A registered user with the Nurse role who has read-only access to records of Patients under their care.
- **Lab_Technician**: A registered user with the Lab Technician role who may create and read lab-result records.
- **Access_Token**: A short-lived JWT used to authenticate API requests.
- **Refresh_Token**: A long-lived JWT used to obtain a new Access_Token without re-authentication.
- **TOTP**: Time-based One-Time Password generated by a compatible authenticator app (RFC 6238).
- **Consent_Grant**: A time-limited, patient-approved record that permits a specific Doctor to access specific Patient records.
- **Nonce**: A unique, single-use token included in sensitive requests to prevent replay attacks.
- **Audit_Entry**: An immutable log record that captures who did what, when, and on which resource.
- **Chain_Hash**: A SHA-256 hash computed over the current Audit_Entry concatenated with the hash of the previous entry.

## Requirements

### Requirement 1: User Registration

**User Story:** As a healthcare institution administrator, I want to register users with assigned roles, so that only authorised personnel can access the system.

#### Acceptance Criteria

1. WHEN a registration request is received with a unique email, valid password, and a role from {Patient, Doctor, Nurse, Lab_Technician}, THE Auth_Module SHALL create a new user account and store a bcrypt hash of the password.
2. WHEN a registration request is received with an email that already exists in the system, THE Auth_Module SHALL return HTTP 409 with a descriptive error message and SHALL NOT create a duplicate account.
3. WHEN a registration request is received with a password shorter than 12 characters, THE Auth_Module SHALL return HTTP 422 with a descriptive validation error.
4. WHEN a registration request is received with a role value outside {Patient, Doctor, Nurse, Lab_Technician}, THE Auth_Module SHALL return HTTP 422 with a descriptive validation error.
5. THE Auth_Module SHALL store passwords exclusively as bcrypt hashes and SHALL NOT store plaintext passwords at any point.

---

### Requirement 2: User Login and JWT Issuance

**User Story:** As a registered user, I want to log in with my credentials and receive tokens, so that I can authenticate subsequent API requests.

#### Acceptance Criteria

1. WHEN a login request is received with a valid email and correct password and MFA is not yet enabled for the account, THE Auth_Module SHALL return an Access_Token with a 15-minute expiry and a Refresh_Token with a 7-day expiry.
2. WHEN a login request is received with a valid email and correct password and MFA is enabled for the account, THE Auth_Module SHALL return HTTP 200 with a partial-auth token and SHALL NOT issue a full Access_Token until a valid TOTP code is submitted.
3. WHEN a login request is received with an incorrect password or non-existent email, THE Auth_Module SHALL return HTTP 401 with a generic error message and SHALL NOT reveal whether the email exists.
4. THE Auth_Module SHALL embed the user's role and user ID as claims inside every issued Access_Token.
5. WHEN an Access_Token has expired, THE Auth_Module SHALL reject the request with HTTP 401.

---

### Requirement 3: Token Refresh

**User Story:** As an authenticated user, I want to exchange a valid Refresh_Token for a new Access_Token, so that my session continues without re-entering credentials.

#### Acceptance Criteria

1. WHEN a token-refresh request is received with a valid, unexpired Refresh_Token, THE Auth_Module SHALL issue a new Access_Token with a 15-minute expiry.
2. WHEN a token-refresh request is received with an expired or revoked Refresh_Token, THE Auth_Module SHALL return HTTP 401 and SHALL NOT issue a new Access_Token.
3. WHEN a Refresh_Token is used to obtain a new Access_Token, THE Auth_Module SHALL invalidate the consumed Refresh_Token and issue a replacement Refresh_Token (token rotation).

---

### Requirement 4: Multi-Factor Authentication (TOTP)

**User Story:** As a registered user, I want to enable TOTP-based MFA on my account, so that my account is protected against credential theft.

#### Acceptance Criteria

1. WHEN a user requests MFA enrollment, THE Auth_Module SHALL generate a TOTP secret using pyotp, return a provisioning URI compatible with standard authenticator apps, and store the secret in encrypted form.
2. WHEN a user submits a valid 6-digit TOTP code during MFA enrollment confirmation, THE Auth_Module SHALL mark MFA as enabled on the account.
3. WHEN a user submits an invalid or expired TOTP code during MFA enrollment confirmation, THE Auth_Module SHALL return HTTP 400 and SHALL NOT enable MFA on the account.
4. WHEN a login request requires MFA and a valid TOTP code is submitted within the 30-second window, THE Auth_Module SHALL complete authentication and issue a full Access_Token and Refresh_Token.
5. WHEN a login request requires MFA and an invalid TOTP code is submitted, THE Auth_Module SHALL return HTTP 401 and SHALL NOT issue tokens.

---

### Requirement 5: Role-Based Access Control

**User Story:** As a system operator, I want every API endpoint to enforce role-based access control, so that users can only perform actions permitted by their role.

#### Acceptance Criteria

1. WHEN a request arrives at a protected endpoint, THE RBAC_Middleware SHALL extract and verify the Access_Token signature and expiry before allowing the request to proceed.
2. WHEN a request arrives at a protected endpoint and the Access_Token is missing or invalid, THE RBAC_Middleware SHALL return HTTP 401.
3. WHEN a request arrives at a protected endpoint and the user's role is not in the set of permitted roles for that endpoint, THE RBAC_Middleware SHALL return HTTP 403.
4. THE RBAC_Middleware SHALL enforce the following role permissions:
   - Patient: read and update own profile; view own records; approve/revoke Consent_Grants.
   - Doctor: read own profile; request Consent_Grants; read Patient records covered by an active Consent_Grant.
   - Nurse: read own profile; read Patient records for Patients explicitly assigned to them.
   - Lab_Technician: read own profile; create lab-result records; read lab-result records they created.
5. WHEN a Doctor attempts to read a Patient record without an active Consent_Grant, THE RBAC_Middleware SHALL return HTTP 403.

---

### Requirement 6: Consent Management

**User Story:** As a Patient, I want to control which Doctors can access my medical records and for how long, so that my health data is shared only with my explicit approval.

#### Acceptance Criteria

1. WHEN a Doctor submits a consent request specifying a Patient ID and a requested access duration in days, THE Consent_Module SHALL create a pending Consent_Grant and notify the Patient.
2. WHEN a Patient approves a pending Consent_Grant, THE Consent_Module SHALL set the grant status to active and record an expiry timestamp equal to the current time plus the requested duration.
3. WHEN a Patient rejects a pending Consent_Grant, THE Consent_Module SHALL set the grant status to rejected and SHALL NOT allow the Doctor to access the Patient's records under that grant.
4. WHEN a Patient revokes an active Consent_Grant, THE Consent_Module SHALL set the grant status to revoked and the RBAC_Middleware SHALL deny the Doctor access within the same request cycle.
5. WHEN an active Consent_Grant's expiry timestamp is in the past, THE Consent_Module SHALL treat the grant as expired and THE RBAC_Middleware SHALL deny access as if no grant exists.
6. THE Consent_Module SHALL allow a Patient to list all Consent_Grants associated with their account, including status and expiry.

---

### Requirement 7: Medical Records CRUD

**User Story:** As an authorised healthcare provider, I want to create, read, update, and delete medical records, so that patient health information is accurately maintained.

#### Acceptance Criteria

1. WHEN an authorised user submits a create-record request with valid record data, THE Records_Module SHALL persist the record and return HTTP 201 with the created record's ID.
2. WHEN an authorised user submits a read-record request for an existing record ID, THE Records_Module SHALL return the decrypted record data.
3. WHEN an authorised user submits an update-record request for an existing record ID with valid data, THE Records_Module SHALL update the record and return HTTP 200.
4. WHEN an authorised user submits a delete-record request for an existing record ID, THE Records_Module SHALL soft-delete the record and return HTTP 200.
5. WHEN any user submits a request for a record ID that does not exist, THE Records_Module SHALL return HTTP 404.
6. WHEN any user submits a request for a record belonging to a different Patient without an active Consent_Grant or role permission, THE RBAC_Middleware SHALL return HTTP 403 before THE Records_Module processes the request.

---

### Requirement 8: AES-256 Field-Level Encryption

**User Story:** As a system operator, I want all sensitive medical record fields to be encrypted at rest, so that a database breach does not expose patient health information in plaintext.

#### Acceptance Criteria

1. WHEN a medical record is persisted to the database, THE Records_Module SHALL encrypt all sensitive fields using AES-256-GCM before writing to the database.
2. WHEN a medical record is retrieved from the database, THE Records_Module SHALL decrypt all sensitive fields using AES-256-GCM before returning data to the caller.
3. THE Key_Manager SHALL load the AES-256 encryption key exclusively from environment variables and SHALL NOT accept a key from any other source.
4. THE Key_Manager SHALL reject application startup if the encryption key environment variable is absent or if the key length is not 32 bytes.
5. THE System SHALL NOT store the AES-256 encryption key in the database, in source code, or in any version-controlled file.
6. FOR ALL medical records, encrypting a record's sensitive fields and then decrypting the result SHALL produce data identical to the original plaintext (round-trip property).

---

### Requirement 9: Replay Attack Protection

**User Story:** As a system operator, I want sensitive endpoints to reject replayed requests, so that captured HTTP traffic cannot be reused by an attacker.

#### Acceptance Criteria

1. WHEN a request arrives at a replay-protected endpoint, THE Replay_Guard SHALL require a Nonce and a UTC timestamp in the request headers.
2. WHEN a request arrives with a Nonce that has been seen within the last 5 minutes, THE Replay_Guard SHALL return HTTP 400 and SHALL NOT process the request.
3. WHEN a request arrives with a timestamp that differs from the server's current UTC time by more than 5 minutes, THE Replay_Guard SHALL return HTTP 400 and SHALL NOT process the request.
4. WHEN a request arrives with a valid, unseen Nonce and an in-window timestamp, THE Replay_Guard SHALL record the Nonce and allow the request to proceed.
5. THE Replay_Guard SHALL apply replay protection to all authentication endpoints and all medical record write endpoints.

---

### Requirement 10: Append-Only Audit Logging

**User Story:** As a compliance officer, I want every sensitive action to be recorded in a tamper-evident audit log, so that I can detect unauthorised access or modification of patient data.

#### Acceptance Criteria

1. WHEN any of the following events occurs — user login, record create, record read, record update, record delete, consent request, consent approval, consent revocation — THE Audit_Module SHALL append an Audit_Entry containing: event type, actor user ID, target resource ID, timestamp, and client IP address.
2. THE Audit_Module SHALL compute a Chain_Hash for each Audit_Entry by hashing the serialised entry concatenated with the Chain_Hash of the immediately preceding entry.
3. THE Audit_Module SHALL use a fixed sentinel hash value of 64 zero characters as the Chain_Hash of the entry preceding the first entry.
4. WHEN a verification request is received, THE Audit_Module SHALL recompute the Chain_Hash for every entry in sequence and return a verification result indicating whether the chain is intact.
5. THE Audit_Module SHALL NOT permit update or delete operations on any existing Audit_Entry.
6. FOR ALL sequences of Audit_Entries, recomputing the chain from the first entry SHALL produce the same Chain_Hash as the stored value on every entry when no tampering has occurred (chain integrity property).

---

### Requirement 11: Secure Configuration Management

**User Story:** As a developer, I want all secrets and environment-specific values to be loaded from environment variables, so that no sensitive data is committed to version control.

#### Acceptance Criteria

1. THE System SHALL load all secrets — including JWT signing keys, AES-256 encryption keys, database credentials, and TOTP encryption keys — exclusively from environment variables or a `.env` file that is excluded from version control.
2. WHEN the System starts and any required secret environment variable is absent, THE System SHALL terminate startup with a descriptive error message identifying the missing variable.
3. THE System SHALL NOT contain any hardcoded secret values in source code, configuration files, or migration scripts.
4. THE System SHALL provide a `.env.example` file listing all required environment variable names with placeholder values and descriptions, committed to version control.

---

### Requirement 12: Transport Security

**User Story:** As a system operator, I want all API communication to occur over TLS, so that data in transit is protected from interception.

#### Acceptance Criteria

1. WHILE running in local development mode, THE System SHALL accept HTTPS connections using a self-signed TLS certificate and SHALL NOT serve plaintext HTTP on any port.
2. THE System SHALL be configurable to use a CA-signed certificate for production deployment without code changes, using only environment variable updates.
3. THE System SHALL expose a health-check endpoint accessible over HTTPS that returns HTTP 200 when the service is operational.

---

### Requirement 13: Password Reset

**User Story:** As a registered user, I want to securely reset my password if I forget it, so that I can regain access to my account without compromising system security.

#### Acceptance Criteria

1. WHEN a user submits a password-reset request with a registered email, THE Auth_Module SHALL generate a cryptographically random, single-use reset token with a 30-minute expiry and send it to the user's registered email address via SMTP, or, WHERE the System is running in development mode, return the token in the response body clearly marked as dev-only.
2. WHEN a user submits a password-reset request with an email that does not exist in the system, THE Auth_Module SHALL return HTTP 200 with a generic message and SHALL NOT reveal whether the email exists.
3. WHEN a user submits a valid, unexpired reset token along with a new password that meets the password policy, THE Auth_Module SHALL update the password hash and invalidate the reset token.
4. WHEN a user submits an expired or already-used reset token, THE Auth_Module SHALL return HTTP 400 and SHALL NOT update the password.
5. WHEN a password reset is completed successfully, THE Auth_Module SHALL invalidate all existing Refresh_Tokens for that user account.
6. WHEN a password reset is completed for an account with MFA enabled, THE Auth_Module SHALL require TOTP verification before the next login proceeds to full token issuance.
7. THE Replay_Guard SHALL apply replay protection to the password-reset request endpoint.
